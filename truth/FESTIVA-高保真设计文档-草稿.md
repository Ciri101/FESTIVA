## 1. 产品与设计目标

FESTIVA 面向希望发现、创建和参加节日聚会的国际学生。现有页面用「Join / Create / Me」组织三类主要操作，并在各模块提供相应 AI 对话入口。设计重点是让用户快速看懂聚会内容、时间地点、费用、参加条件，以及自己下一步能做什么。

本文件分开记录**画面已呈现的事实**和**待确认的交互/决策**。截图里的姓名、学校、地址、日期、人数、认证标识和匹配百分比均视为样例内容，不代表真实数据或已实现能力。

## 3. 信息架构与主要路径

静态画面显示三个底部主入口：**Join、Create、Me**。每个主入口右侧另有角色头像入口：Join 对应 Patti，Create 对应 Conor，Me 对应 Lily。AI 对话页使用顶部返回导航与底部输入框，不显示三栏底部导航。

从画面可归纳的目标路径如下；箭头表示合理的页面关系，实际跳转仍需原型验证：

```text
Join 首页 → Filter / Party Details → Send request
Join 首页 → Patti 对话 → 推荐活动卡 → Party Details（待验证）
Create 首页 → Create Party 表单 → 创建结果/派对管理（截图缺失）
Create 首页 → Notice → 审核申请（结果页与状态未展示）
Create 首页 → Conor 对话 → 派对草稿卡 → 表单/预览（待验证）
Me 首页 → 收藏/历史/个人资料/设置（子页面未提供）
Me 首页 → Lily 对话 → 资料修改确认（确认页未提供）
```

## 4. 页面设计说明

### 4.1 Join 首页（278）

- 顶部为带放大镜的搜索框，右侧是筛选按钮。
- “Popular tags” 用胶囊标签呈现；示例中 `Traditional food` 为黄色选中态，其余为灰色未选中态。
- “Recommend Party” 使用纵向活动列表。每项左侧方形圆角图片，右侧显示主办人、Verified 标识、活动名称、日期和地点；部分卡片右上角有黄色匹配百分比。
- 底部导航的 Join 项以白色凸起底座、黄色图标和文字表示选中；角色头像独立放在导航右侧。

**需定义**：搜索结果及输入联想、标签多选规则、列表排序与空状态、匹配百分比的真实计算依据、点击活动卡的跳转与加载状态。

### 4.2 Filter（280）

- 上半部分是地图及圆形范围覆盖层；下半部分为可滚动的筛选面板。
- 可见条件：节日、距离（km）、交通方式、预算（CAD）、时间段、语言、Home/Restaurant 场地类型。
- 底部黄色 Search 按钮提交筛选。

**需定义**：各条件是否可不填、距离基于哪个起点、拖动范围与数值输入关系、预算边界、交通时间是否参与筛选、地图定位权限、条件重置和无结果状态。图片中的 `3/8/15` 与 `15/35/60` 只是刻度示例，不能当作固定选项。

### 4.3 Party Details（276）

- 顶部大图与活动标题，下方是主办人及 Verified 标识。
- 主要操作是 `Send request` 与 `Favorite`；右侧显示 `6/8 joined`。
- 显示日期时间、地址、地图缩略图、活动介绍、预算、聚会场地与加入规则。
- 页面右上角有分享图标。

**需定义**：报名后的按钮状态与审批反馈、收藏状态、分享行为、地图点击后的去向、地址公开精度、时间的时区、活动满员和取消场景。`6/8 joined` 是状态数据，不应被误实现为可操作按钮。

### 4.4 Create 首页（296）与表单（275）

- Create 首页上方有通知铃铛和加号，下方列出“我主持的派对”，沿用活动图片、主办人、标题、时间与地点的信息结构。
- 创建表单有大幅封面及图片入口，分为 Basic information、Join in、Rules 三段。可见字段包括名称、开始时间、聚会类型、地址、介绍、最大人数、是否审核、预算与规则。
- 底部黄色 `Create` 按钮是主操作。

**需定义**：字段类型、必填项、时区、价格单位、发布前预览、草稿保存、图片版权/上传流程、成功后落点和后续管理操作。截图只显示单页表单，不能推断 `Create` 点击后立即公开发布。

### 4.5 Notice / 主办方审核（281）

- 顶部 `New` 和 `Past` 分段切换。
- 新申请列表显示头像、申请人姓名、学校认证文字、目标派对，以及右侧 `×`、`✓` 两个图标按钮。
- 页面底部仍保留 Create 选中态和 Conor 入口。

**需定义**：点击拒绝/批准是否二次确认、审批后提示与列表去向、容量已满和重复操作处理、申请人详情、历史记录内容，以及按钮的可访问性标签。截图仅能证明存在两个审批动作，不能证明已经实现状态机。

### 4.6 Me 首页（297）

- 顶部展示头像、姓名、学校与 Verified 标识。
- `Party record` 下是 Favorite parties、Past parties；`My data` 下是 Address、Personality、Food Allergy、Language、Culture & Religion、Settings。
- 列表项使用左图标、中标题、右箭头；整体主要靠留白和分隔线建立层级。

**需定义**：资料编辑页面、地址可保存的数量与用途、认证信息来源、隐私可见范围、当前报名及正在主持的活动是否有独立入口。图中未展示这些内容。

### 4.7 三个 AI 对话页（272–274）

| 角色 | 截图中呈现的用途 | 需要确认的结果动作 |
| --- | --- | --- |
| Patti | 根据语言、节日、食物等需求推荐活动并追问氛围偏好 | 推荐卡打开详情；重新推荐与筛选边界 |
| Conor | 从用户描述提取创建要求，展示一张派对草稿卡 | 草稿卡打开表单/预览；用户确认后才创建或发布 |
| Lily | 倾听用户描述的社交风格，讨论适合的聚会环境 | 将建议展示给用户确认后再写入资料 |

三个页面共用顶部角色名与副标题、浅米色用户消息气泡、灰色助手文字和底部输入条。对话页底部占位文字都写成 `Chat with Conor`，与 Patti、Lily 页面不符；应按角色变化。当前图片没有显示跨角色共享对话内容的依据。

## 5. 视觉语言与组件

- **色彩**：大面积白底，黄色承担主按钮、导航选中态、认证勾选和部分强调；橙色用于主办人/身份辅助文字；灰色用于次要信息和图标。具体色值需从源设计文件提取，不能凭截图定稿。
- **文字**：标题使用黑色或深灰的较大粗体，正文与元信息使用灰色。字号、字体、字重与行高须从设计源文件核对；仅凭 JPG 不能确认精确 token。
- **图片**：食物与聚会照片强化节日氛围，活动列表采用左图右文；详情和创建页采用顶部大图。
- **控件**：圆角搜索框、标签、输入框、主按钮和底部导航；部分控件使用灰色描边，部分使用阴影。正式组件库需统一尺寸、圆角、描边/阴影与状态。
- **系统适配**：截图为固定尺寸 iPhone 画布。实现时要验证安全区、长文本、动态字体、屏幕尺寸、键盘遮挡和滚动，而不能以截图像素固定布局。

## 6. 需要优先修正或确认的画面问题

1. **数据一致性**：同一批示例活动出现 2025 与 2026 年日期，个别日期与星期文字、地点缩写也应统一核对。截图数值仅作为样例。
2. **错误的对话占位文案**：Patti 和 Lily 页面仍显示 `Chat with Conor`。
3. **未证实的断言**：`Verified`、学校认证及 `93%/88%/87% match` 需要真实规则和数据来源；未实现时不能作为产品事实展示。
4. **地点与隐私**：详情图中直接显示精确街道地址和地图位置，需要确认申请获批前的可见范围。
5. **时间信息**：活动详情未显示时区；跨地区用户可能误解时间。
6. **创建按钮布局**：表单底部的 `Create` 按钮覆盖/紧贴 Rules 输入区，需验证内容滚动与键盘打开时的间距。
7. **审批可理解性**：申请列表的叉号和勾号缺少文字说明；需要明确拒绝、批准及操作反馈。
8. **页面覆盖不足**：缺搜索联想、申请结果、活动管理、空/错误状态，以及 Me 子页面；不能仅凭当前图片完成全部交互验收。

## 7. 建议的设计验收清单（待批准）

- 主导航、角色入口及返回路径在原型中均可走通。
- 用户能从推荐卡看懂活动名称、时间、地点、费用和加入限制，并打开详情。
- 筛选条件、标签状态和结果列表保持一致；无结果、未定位和加载失败时有清晰反馈。
- 创建表单可在键盘开启和较大字体下完整填写；提交前能识别缺失字段。
- 申请、收藏、主办方审批均有明确的进行中、成功和失败反馈。
- AI 生成的建议先呈现给用户确认，不能直接把示例文案当成已保存数据。
- 所有认证、人数、费用、匹配解释和活动状态都能对应真实数据来源。

以上清单是基于截图提出的设计验收建议，不表示这些行为已由图片验证或已获批准。
