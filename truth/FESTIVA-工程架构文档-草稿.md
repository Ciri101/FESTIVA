## 1. 项目与文档范围

FESTIVA 是面向国际学生的 iOS 节日聚会应用。用户在 App 中发现、创建和加入聚会，检查活动是否符合自己的时间、预算和交通条件，并获得可解释的推荐。

本文按所给 C4 图的 Context Level 和 Container Level，记录系统边界、组件职责、主要数据流和工程待决问题。图中没有给出的接口字段、部署拓扑、供应商和验收指标均不在此处擅自确定。

## 2. 系统上下文（C4 Context Level）

| 对象 | 图中职责 | 与 FESTIVA 的关系 |
| --- | --- | --- |
| International Student | 发现、创建、加入节日聚会；检查匹配度、时间、花费和交通 | 主要用户 |
| iOS Mobile App / Party App (Mobile) | 学生验证、偏好设置、聚会推荐与筛选、创建与加入、日程和安全相关体验 | FESTIVA 客户端 |
| Cloud LLM Service / AI Inference Service | 生成可解释的聚会推荐和文化提示 | 外部系统 |
| Geolocation Service / Map & Routing API | 提供地点、距离、路线、预计通行时间和交通方式 | 外部系统 |

用户通过 iOS App 完成核心操作。App 在需要推荐解释或文化提示时使用 AI 能力，在需要距离和通勤信息时使用地图能力。图中的“verified peers”是产品目标表述；验证方式、可信等级及展示规则尚未定义，不能据此宣称用户已通过某种具体认证。

## 3. 容器结构（C4 Container Level）

| 容器 | 已在图中表达的职责 | 图中技术标注 |
| --- | --- | --- |
| Party App (Mobile) | 学生验证、偏好、推荐、筛选、创建、加入、日程和安全体验 | SwiftUI / Swift |
| Embedded Recommendation Module | 收集推荐上下文；展示排序、匹配理由、差异与限制；不是独立通用聊天助手 | Swift module / on-device rules |
| API & Networking / Networking System | 协调 App、推荐逻辑、数据库和经批准的外部 API；在软偏好前应用主办方要求 | API service，具体技术待验证 |
| Application Database / Database | 保存已验证资料、偏好、聚会、主办方要求、成员关系、收藏、日程约束及推荐反馈 | PostgreSQL |
| Cloud LLM Service / AI Inference Service | 生成可解释的推荐内容和文化提示 | 外部系统；供应商未指定 |
| Geolocation Service / Map & Routing API | 提供地点、路线、距离、预计通行时间和交通方式 | 外部系统；供应商未指定 |

推荐模块嵌入 iOS 客户端，负责收集条件与呈现结果；图中并未把它定义成可独立部署的服务。API 服务是应用数据的服务端入口。PostgreSQL 是图中标出的数据存储技术，但具体表结构尚未设计。

## 4. 图中明确的连接与数据流

1. **用户 → iOS App**：发现、创建或加入节日聚会。
2. **iOS App → API & Networking**：通过 JSON / HTTPS 提交业务请求，并取得应用数据。
3. **iOS App → Embedded Recommendation Module**：提供资料、筛选条件及当前约束；模块显示推荐结果与解释。
4. **Embedded Recommendation Module → API & Networking**：通过 JSON / HTTPS 请求排序结果及解释。图中要求服务端先处理主办方要求，再考虑参与者软偏好。
5. **API & Networking ↔ Application Database**：读取和写入用户资料、活动、成员关系、偏好与反馈等应用数据。
6. **iOS App / 服务端与 Geolocation Service**：图中出现地点、路线和 ETA 的调用关系，但调用发起方与数据返回路径需进一步澄清。
7. **AI 能力**：图中同时画有 App 向 Cloud LLM Service 提交上下文，以及推荐流程通过服务端请求解释结果的路径；最终由客户端直连还是服务端代理尚未确定。

上述连接是架构图表达的逻辑关系，不等同于已完成的接口契约。箭头未说明的认证、错误处理、缓存与调用频率仍需定义。

## 5. 推荐链路的工程约束

图中明确要求**主办方硬性要求先于参与者软偏好**。因此，推荐处理应至少区分两阶段：

1. 根据可验证的资格与硬性条件筛除不符合的活动；未取得必要信息时，不将其默认为符合。
2. 对剩余活动按偏好排序，并生成可供用户理解的匹配理由、差异和限制。

客户端推荐模块展示结果，服务端负责对权威应用数据和主办方要求进行校验。LLM 可参与解释生成，但不能代替容量、报名资格、审批状态或其他服务端事实的判定。具体排序规则、缺失值处理、反馈闭环与解释格式仍待设计。

## 6. 数据边界与状态

图中列出的数据库数据类型包括：已验证资料、用户偏好、聚会记录、主办方要求、成员关系、收藏、日程约束和推荐反馈。这些是**概念数据域**，不是已经批准的数据库表或字段。

工程设计时需要进一步定义：

- 用户与聚会的唯一标识、活动时间与时区、地点精度及可见范围。
- 加入申请、主办方审批、成员关系和容量的状态转换。
- 哪些用户资料可以进入推荐请求，哪些可以发送给外部 AI 或地图服务。
- 资料验证结果的来源、有效期和撤销方式。
- 收藏、反馈和日程约束的保存及删除规则。

涉及报名、容量和审批的写入应以服务端状态为准，避免客户端显示与真实状态不一致。具体并发控制方案尚未由 C4 图确定。

## 7. 安全、隐私与可靠性设计要求（待细化）

图中把学生验证和安全列为客户端能力，把 API 服务称为安全协调层，但未给出实现机制。正式工程方案至少需要明确：身份认证与授权、传输加密、服务端权限检查、敏感资料访问控制、日志脱敏、第三方数据传输范围，以及聚会地点的可见性规则。

还需定义外部 LLM 或地图服务不可用时的降级行为。例如，推荐解释失败不应导致已存在的活动数据丢失；地图 ETA 不可得时应清楚标为未知，而不是给出推测值。具体服务等级、监控指标和恢复目标待确认。
