## 1 视图注记

- **本族**：API 服务的 12 个组件（浅蓝，`class … shell`），都在标签为“API 服务”的系统框内。灰色节点是 C2 中与 API 服务相连的容器与外部系统，名称与 [C2](../festiva-c2/festiva-c2.md) 一致。
- **布局**：三个分组框近似六边形布局（规范第 7 节）。“接入”在上，是驱动侧的适配器；“业务核心”居中；“适配器”在下，是被驱动侧的技术件。分组框只是布局，不是容器。
- **设计要点**（任务 T0018 第 1 步的决定）：
  - **纯规则加一个编排者**：活动目录、申请账本、用户档案、推荐排序、通知箱都是不碰存储、不取当前时间的纯规则。业务用例负责一次操作的先后：读数据、调用规则、在同一个事务里写回、事后发推送。它自己不做业务判断。这与 Demo 的结构一一对应：LocalFestivaAPI 调用 Domain 的规则函数，RankingEngine 是纯函数。
  - **接口归中心侧**：存取口、会话口、图片上传口、邮件口、推送口都由业务用例定义，由外圈适配器实现（边 10–14，耦合为“两者反向”）。外部技术只出现在适配器与外部节点之间（边 15–18）。
  - **事务**：一次业务操作对应一个数据库事务，由业务用例开启和提交。名额检查与状态写入（C4、S7-1）、修改性别后的连带撤回与退出（U4；T0027 推广到两个性别）、随状态变更写入的通知记录（工程架构文档第 9 节），都在同一个事务里完成。
  - **当前时间**：由业务用例传给规则。正式版取服务端时间；Demo 取演示时钟，只替换这一处。
  - **只读接口**：AI 编排服务与 App 从同一个 HTTP 接口适配器进入，使用同一套会话令牌，但 AI 只能调用只读的部分（边 2），对应 Demo 中 AI 只拿到 FestivaReadAPI。
  - **实现要点（观察 O2）**：业务用例连出 10 条边，是全图的枢纽。只要它不做业务判断，就不算上帝组件；但实现时最容易把判断顺手写进去，这是评审与代码审查的重点，Demo 的 LocalFestivaAPI 同样适用。判断一律放进规则组件，业务用例的代码里只出现“读取、调用规则、写回、推送”。
- **Demo 专用的部分不画**：演示时钟、种子导入、演示账号切换不在正式架构里，只在第 2 节“Demo 对应”一栏说明。

## 2 组件注记

“类”按规范第 4 节的四个问题判断：规则变了是否必须改它、业务方能否判断它的对错、换个行业是否还需要它、市面上能否买到。

| 组件 | 英文名 | 类 | 一句职责 | 依赖谁 | Demo 对应 |
| --- | --- | --- | --- | --- | --- |
| HTTP 接口适配器 | HTTP API adapter | 技术 | 负责把 HTTP 请求鉴权后转成用例调用，不负责任何业务判断 | 会话签发器、业务用例 | 无：Demo 中界面直接调用本机的业务接口 |
| 业务用例 | business use cases | 业务 | 负责编排一次操作的读取、规则调用、事务提交与事后推送，不负责业务判断 | 五个核心组件、五个适配器 | Data 模块的 LocalFestivaAPI（实现 FestivaAPI） |
| 活动目录 | party catalog | 业务 | 负责活动的发布、修改、取消与状态计算，不负责申请与名额 | — | Domain 中活动的规则函数；节日与标签列表的读取 |
| 申请账本 | membership ledger | 业务 | 负责申请状态的转换与名额判定，不负责活动本身的内容 | — | Domain 中申请与名额的规则函数 |
| 用户档案 | user profile | 业务 | 负责资料、学校认证状态与字段可见范围，不负责验证码与令牌 | — | Domain 中资料与可见范围的规则函数；收藏、AI 同意记录 |
| 推荐排序 | recommendation ranking | 业务 | 负责硬条件过滤、软偏好计分与理由标签，不负责读取数据 | — | Domain 的 RankingEngine |
| 通知箱 | notification inbox | 业务 | 负责决定每个事件的接收人并生成站内通知，不负责投递 | — | Domain 中通知的规则函数（NotificationInbox）；设备令牌登记在 Demo 中没有（Demo 没有推送） |
| 会话签发器 | session issuer | 技术 | 负责验证码与会话令牌的生成和校验，不负责判断谁能注册 | — | 无：Demo 为预置认证与演示账号切换 |
| 数据库适配器 | database adapter | 技术 | 负责按存取口读写数据库，不负责业务判断 | 数据库 | Data 模块的 SwiftData 模型与存取 |
| 图片上传签名器 | image upload signer | 技术 | 负责签发上传地址与校验已上传的图片，不负责决定谁能上传 | 文件存储 | Data 模块的图片文件存取（App 沙盒） |
| 邮件适配器 | email adapter | 技术 | 负责经邮件服务商发送验证码邮件，不负责验证码的生成 | 邮件发送服务 | 无 |
| 推送通知适配器 | push notification adapter | 技术 | 负责经 APNs 发送推送，不负责决定通知谁 | Apple 推送通知服务 | 无：Demo 只有站内通知 |

小项的归属（任务 T0018 第 1 步的决定）：收藏与 AI 同意记录归用户档案，设备令牌归通知箱，节日、标签与语言列表归活动目录。这些列表由运营直接维护在数据库中，本服务只读，不提供维护接口（任务 [T0025](../../../queue/tasks/T0025/task.md)）。

## 4 主要用例的走向

以下写的是业务用例怎样调用各组件，供 Demo 与将来的服务端实现对照；规则本身以产品设计文档为准。

- **申请活动**：经存取口读出活动、申请人的资料与该活动的申请 → 活动目录算出活动状态 → 申请账本判定资格与名额，给出新状态（申请中，或无需审核且有名额时直接已加入）→ 通知箱给出接收人 → 在同一事务中写入申请与通知 → 事后推送。
- **主办人审批**：读出申请与活动 → 申请账本判定能否通过（已满时不能通过）→ 通知箱给出申请人 → 同一事务写入 → 事后推送。
- **取消活动**：活动目录判定能否取消 → 申请账本给出受影响的“申请中”“已加入”记录 → 通知箱给出接收人 → 同一事务写入 → 事后推送。
- **修改性别**：用户档案与申请账本给出与新性别不符、未结束且未取消的限定活动（修改前先返回给 App 提示；已取消活动的记录已冻结，V2）→ 确认修改后，在同一事务中改性别、撤回或退出、释放名额、写入给主办人的通知 → 事后推送。
- **推荐与搜索**：读出候选活动与用户资料（候选活动一次读出，在内存中过滤排序；活动多时先在数据库侧粗过滤，任务 T0025）→ 推荐排序过滤、计分、生成理由标签 → 活动目录按查看者过滤字段后返回。
- **注册与登录**：用户档案判定邮箱域名属于哪所学校 → 会话签发器生成验证码 → 邮件适配器发送 → 核对后会话签发器签发令牌。

## 5 待确认事项

> 评审清单回执是某次评审的验证证据，写在对应任务的回执里（规范第 9、10 节）。本图定稿以来的评审清单回执与回述，原样迁移在任务 [T0032](../../../queue/tasks/T0032/task.md) 的回执中。

以下事项经任务 [T0025](../../../queue/tasks/T0025/task.md) 决定，实现正式版时再定：

- **验证码与会话**：验证码的有效期、重试次数、重发间隔与发送频率限制，以及退信的处理；会话令牌的有效期与续期。
- **并发与幂等**：并发申请与并发审批（包括多实例运行）时事务的隔离级别与加锁方式；业务接口的幂等，例如重复提交申请、重复点击“通过”。
- **通知与推送**：通知记录与推送的幂等，推送失败后是否重试；设备令牌失效后的清理。
- **图片**：图片地址公开还是带签名；签名地址的有效期；已上传但没有被活动引用的图片怎么清理；图片内容审核。
- **限流与来源**：AI 只读查询的限流；AI 编排服务与 App 的请求怎样区分来源（令牌作用域，还是单独的入口）。
