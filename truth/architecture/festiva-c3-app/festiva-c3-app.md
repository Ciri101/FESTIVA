## 1 视图注记

- **本族**：iOS App 的 17 个组件（浅蓝，`class … shell`），都在标签为“iOS App”的系统框内。灰色节点是 C2 中与 iOS App 相连的人、容器与外部系统，名称与 [C2](../festiva-c2/festiva-c2.md) 一致。
- **MVVM 三层**（用户决定按 MVVM 设计，按三层分组，任务 T0019）：
  - **界面层（View）**：SwiftUI 界面，只渲染视图模型给出的状态，把用户操作转交给视图模型；不调用业务接口，不做判断。界面与视图模型按板块成对：登录、Join、Create、Me、对话。
  - **视图模型层（ViewModel）**：每个板块一个，持有页面状态、用户流程与确认卡片的状态；调用模型层的接口。**视图模型不做业务判断**：能否申请、名额是否已满、按钮显示什么（S9-1）、资料哪些字段可见，都以业务接口返回的结果为准，视图模型只负责呈现。代码里每个页面可以有自己的 ViewModel，放在板块目录下，属于代码层，本图不画。
  - **模型层（Model）**：业务接口与值类型住与服务端共用的 Domain 包，形状见 [API 服务 C3](../festiva-c3-api/festiva-c3-api.md) 边 4，本图不单独画框；图上画的是实现这些接口的适配器。接口都由中心侧定义，适配器实现（耦合“两者反向”）。
- **布局**：界面层在上，是驱动侧；视图模型层居中；模型层在下，是被驱动侧的技术件。三层分组框就是本容器的六边形布局，板块靠“Join 界面—Join 视图模型”这样的成对命名体现。
- **确认卡片**（B1）：放在对话界面里，由对话视图模型管理。AI 结果只能经确认卡片变成数据：Lily 的资料摘要，由用户逐条确认后经业务接口写入；Conor 的草稿，交给 Create 视图模型预填表单（边 9），用户在表单上点 Create 才发布（B3）；Patti 的推荐卡只用于跳转。
- **整层作为端点**：“视图模型层 → 业务接口客户端”“界面层 → 图片存取适配器”等边以分组框为端点，表示这一层的组件都这样用。规范第 5 节允许带标签的子图作端点。
- **P1 的处理**（用户决定）：地址转坐标、在地图中打开、定位、推送注册都经适配器，接口由 App 定义；界面中直接用系统地图显示区域和位置，接受为平台例外，所以画出“界面层 → Apple 地图服务：显示地图”（边 22）。
- **对话记录**（任务 T0022，依据 T0020 中用户的决定）：保存在手机上，按账号与角色分开，服务端不保存。对话视图模型打开某个角色的对话时，经对话记录存取适配器读出记录；每轮把本角色的记录随新消息交给对话客户端（边 8）；收到回复与卡片后追加保存（边 25）。退出登录不清除，同一台手机换其他账号登录看不到（T0022 中用户的决定）；换手机不迁移。
- **旧卡片**（T0022 中用户的决定）：重新打开对话时，以前的卡片照常可用。推荐卡点进详情，看到的是业务接口返回的最新数据；草稿卡可以再次预填表单，仍须点 Create 才发布；摘要卡可以再次逐条确认后写入。卡片都不会自动写入，B1 不受影响。
- **Demo**：Demo 用同一套界面与视图模型，只替换模型层的实现：业务接口客户端由本机的 LocalFestivaAPI 顶替，对话客户端由 App 内的 AIOrchestrator 顶替，推送注册器不存在；对话记录存取适配器同样存在。演示账号、演示时钟、位置来源、密钥设置等 Demo 专用项不画，写在第 2 节“Demo 对应”一栏。

## 4 主要流程

以下写的是界面、视图模型与模型层怎样配合，供 Demo 实现对照；规则以产品设计文档为准，判断都在 API 服务。

- **浏览与申请**：Join 界面 → Join 视图模型取起点（定位适配器）并经业务接口取推荐 → 界面显示理由标签 → 进入详情，主按钮文字由申请状态决定 → 点 Send request → 视图模型经业务接口申请 → 按返回的新状态更新按钮与提示。
- **主办审批**：Create 界面的铃铛 → Create 视图模型经业务接口取申请列表 → 点通过或拒绝 → 视图模型提交 → 按返回结果把该条移到 Past；已满时“通过”不可用，由接口返回的状态决定。
- **Conor 创建活动**：对话界面 → 对话视图模型经对话客户端得到草稿卡 → 用户点草稿卡 → 对话视图模型把草稿交给 Create 视图模型（边 9）→ 预填表单，“建议”字段有标记 → 上传封面（图片存取适配器）→ 用户点 Create → Create 视图模型经业务接口发布。
- **Lily 整理资料**：对话视图模型得到资料摘要卡 → 用户逐条勾选并确认 → 对话视图模型经业务接口写入选中的条目。
- **打开对话与保存记录**：进入某个角色的对话 → 对话视图模型经对话记录存取适配器读出该账号、该角色的记录 → 界面显示以前的消息与卡片（卡片照常可用）→ 用户发消息，对话视图模型把本角色的记录与新消息经对话客户端发出 → 收到回复与卡片后追加保存。
- **修改性别**：Me 视图模型先经业务接口取得受影响的活动 → 界面提示 → 用户确认后提交 → 显示结果。
- **登录与推送**：登录视图模型经业务接口完成验证码登录 → 经推送注册器注册设备 → 设备令牌经业务接口登记 → 之后收到的推送经推送注册器提示各视图模型刷新。

## 5 评审清单回执（规范第 9 节）

违反项列为问题，编号接续 P1–P4 与 O1、O2。

**依赖方向**

- 跨类别箭头从技术指向业务：界面 → 视图模型（边 2–6）符合；视图模型调用模型层适配器的边（7、8、10、11、13–16、25）运行时方向是业务到技术，但接口都由中心侧定义，耦合写“两者反向”，符合。界面层 → 图片存取适配器（边 12）是技术到技术。
- 每个接口定义在中心侧：边 7 的接口归 API 服务的业务侧，边 8、10–16、25 的口由 App 中心侧定义，界面到视图模型的接口归视图模型，都符合。边 21–23 归 Apple，是适配器的本职；边 22 由界面直接使用系统地图，是 P1 中用户决定接受的平台例外。
- 无循环依赖：推送注册器与视图模型层之间有“注册设备”和“新通知”一来一回（边 16、17），后者是事件投递，推送注册器只依赖中心侧定义的通知口，源码上没有循环。对话视图模型 → Create 视图模型是单向的。符合。

**职责**

- 每个组件一句不含“和”的职责：第 2 节各组件写成“负责 X，不负责 Y”。符合。
- 名称过规范第 6 节七条：板块名沿用产品术语；“界面”“视图模型”“客户端”“适配器”“注册器”是含义固定的角色名词；中英直译成对；没有 manager、service 一类只表地位的词。符合。
- 应用服务层不含业务判断：在本容器里，对应的是“视图模型不做业务判断”。设计上判断全在 API 服务，视图模型只呈现接口返回的结果，符合；但这是 MVVM 最容易走样的地方，列为观察 O3。

**接口**

- 每根线都有边表行并标了具体接口名：25 条边都有边表行。符合。
- 没有组件向所有调用方暴露同一个大接口：初稿不符合，业务接口客户端把整个业务接口暴露给五个视图模型，列为问题 P5。用户决定按板块拆成子接口（边 7），现已符合。
- 接第三家同类供应商要改几个框：业务接口的实现从 LocalFestivaAPI 换成网络客户端、对话的实现从 App 内编排换成服务端，都只换模型层的一个实现，“0 改 1 加”，Demo 本身就是证明。地图显示按 P1 的决定作为例外。符合。
- 测试环境把框换成假实现，上游要不要改：模型层的七个适配器都在中心侧定义的接口后面，视图模型可以用假实现测试，不改。符合。

**耦合与切分**

- 没有两个容器共用数据库表：App 不访问数据库。符合。
- 没有按技术分层切服务：三层是一个容器内部的 MVVM 分层，不是切服务。符合。
- 顶层按业务能力划分，每片内部再分层：本图按用户的决定以 MVVM 三层分组，板块作为成对的组件体现在每一层里，而不是按板块分组。这是有意的取舍，让 MVVM 一眼可见；业务能力的划分仍然完整（五个板块各有一对界面与视图模型）。
- 没有只转发不做决策的胶水组件：视图模型持有页面状态与流程，业务接口客户端负责协议与鉴权，都不只是转发。符合。

**T0013 遗留项的结论**

- P1：已处理。地址转坐标、在地图中打开、定位、推送注册经适配器（边 13–16），接口由 App 定义；界面直接显示系统地图接受为平台例外（边 22）。

## 6 回述（规范第 10 节）

1. **组件职责表**：见第 2 节。
2. **接口清单**：见第 3 节编号边表。
3. **做出的假设**（请用户确认）：
   - 假设 1：视图模型不缓存业务事实，名额、申请状态、认证都以业务接口最新返回的结果为准。
   - 假设 2：会话令牌由业务接口客户端与对话客户端共用，保存在系统钥匙串中；令牌存储是客户端的内部细节，不单独画。
   - 假设 3：推送只作提醒；铃铛角标与我的申请的内容以业务接口返回的通知记录为准（工程架构文档第 9 节）。
   - 假设 4：对话视图模型把 Conor 的草稿交给 Create 视图模型时不写入任何数据。
   - 假设 5：在地图上手动选择起点，是界面在系统地图上的交互，选中的坐标交给 Join 视图模型。
   - 假设 6（T0022）：对话记录只在手机上，换手机或删除 App 后不迁移、不恢复。
4. **规格里没有定义的边界**（需要用户决定）：
   - 边界 1：离线或弱网时的行为，包括是否缓存列表、失败后是否自动重试。
   - 边界 2：流式对话中途断开时，界面怎么处理已收到的部分。
   - 边界 3：会话令牌过期时，自动续期还是回到登录页。
   - 边界 4：用户拒绝推送权限时的替代，例如只靠进入 App 时刷新。
   - 边界 5：图片上传前是否压缩、大小上限，以及失败后的重试。
   - 边界 6：同一账号在多台设备登录时，推送与会话怎么处理。
   - 边界 7（T0022）：对话记录保存多久、占用空间的上限。
   - 边界 8（T0022）：用户能否手动清空某个角色的记录；这需要在产品设计文档中增加功能。
5. **发现的问题**：
   - **P5**：业务接口客户端向五个视图模型暴露同一个大接口（边 7），不符合“没有组件向所有调用方暴露同一个大接口”。后果：任何一个板块的接口变动都会波及全部视图模型，测试时也要为整个接口准备假实现。修法：按板块把业务接口拆成几个子接口（Swift 的协议组合），例如 Join 只需读取与申请，Create 需要活动管理与审批；由同一个客户端（Demo 中是 LocalFestivaAPI）实现，本图结构不变。**用户已决定按此修法处理**（2026-09-29），边 7 的接口栏据此改写。
   - **观察 O3**：视图模型是 MVVM 中最容易混进业务判断的地方，例如自己判断“已满”。评审与代码审查要守住“按接口返回的结果呈现”；这一点与 API 服务 C3 的观察 O2 相呼应。
