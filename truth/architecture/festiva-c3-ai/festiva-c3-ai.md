## 1 视图注记

- **本族**：AI 编排服务的 9 个组件（浅蓝，`class … shell`），都在标签为“AI 编排服务”的系统框内。灰色节点是 C2 中与 AI 编排服务相连的容器与外部系统，名称与 [C2](../festiva-c2/festiva-c2.md) 一致。
- **布局**：三个分组框近似六边形布局（规范第 7 节），与 [API 服务 C3](../festiva-c3-api/festiva-c3-api.md) 相同。“接入”在上，是驱动侧的适配器；“业务核心”居中；“适配器”在下，是被驱动侧的技术件。分组框只是布局，不是容器。
- **设计要点**（任务 T0020 第 1 步中用户的决定）：
  - **纯规则加一个编排者**：角色目录、共享上下文与三个工具组件都是不访问外部、不调用模型的纯规则。对话用例负责一轮对话的先后：经只读接口取同意状态、资料与活动 → 共享上下文决定本轮能发给模型什么 → 角色目录给出提示词与该角色唯一的工具 → 经模型口调用模型 → 模型要求调用工具时，交给该角色的工具组件校验参数，需要数据时经只读接口取得，再由工具组件生成卡片 → 把工具结果交回模型得到回复 → 流式返回回复与卡片。它自己不做业务判断。这与 Demo 的结构对应：AIOrchestrator 调用 AI 模块中的规则。
  - **事实只来自工具结果**（工程架构文档第 5.3 节）：推荐卡、草稿卡、摘要卡都由工具组件用 API 服务返回的数据与校验过的参数生成，模型的文字只作回复。原草稿的“输出校验”因此拆进三个工具组件，各自校验自己的参数；Qwen 的工具调用没有严格模式（任务 [T0016](../../../queue/tasks/T0016/task.md)），参数校验不能省。
  - **只读**（B1）：本容器没有任何写入边，到 API 服务的边都是虚线；API 服务的 HTTP 接口适配器也拒绝来自本容器的写入类请求（API 服务 C3 边 2）。写入只由 App 在用户确认卡片之后经 C2 边 2 完成。
  - **同意**（C9）：放在共享上下文。同意说的就是“哪些内容会发给 AI 服务”，与共享上下文回答的是同一个问题；没有同意时不发送任何用户数据，整轮拒绝。同意状态每轮经只读接口查询。
  - **令牌**：对话接口适配器不自行验证会话令牌，原样交给对话用例，由只读接口客户端带给 API 服务。每轮第一步查同意状态时，API 服务就会校验令牌；令牌无效，在调用模型之前即被拒绝。两个容器不共享签名材料。这回应了 C2 设计说明的假设 1。
  - **对话记录**：保存在用户手机上，服务端不保存；App 每轮把本角色的记录与新消息一起发来（边 1）。本服务因此拿不到其他角色的对话原文，B2 自然成立。App 侧的保存方式由任务 [T0022](../../../queue/tasks/T0022/task.md) 增补到 iOS App C3。
  - **回复时间**：目标是在与使用场景相称的时间内，给出合理的回复与有效的结果（推荐卡、草稿卡、摘要卡）；回复流式返回，用户随时看得到进展。每轮工具调用次数上限与超时只是对话用例防止失控的保护措施，数值按所选型号实测确定，不作为规则；达不到目标时按 S3-1 提示 AI 暂不可用，其他功能照常。
  - **模型口**：由对话用例定义，写在边 8 的接口栏；图上只画实现它的大模型适配器，与前两张 C3 的做法一致。换一家供应商只需新增一个适配器；Demo 的演示脚本 ScriptedLLMClient 是同一个口的另一个实现。
- **Demo 专用的部分不画**：演示脚本、用户自带并存在钥匙串中的密钥、演示时钟给出的“今天”，只在第 2 节“Demo 对应”一栏说明。

## 4 主要流程

以下写的是对话用例怎样调用各组件，供 Demo 与将来的服务端实现对照；规则本身以产品设计文档为准。

- **每轮开始**：对话接口适配器收到请求 → 对话用例经只读接口查同意状态（令牌无效或没有同意即拒绝，不调用模型）→ 读取已确认的资料与用户创建或参加的活动 → 共享上下文给出本轮可发送的字段 → 角色目录给出提示词与唯一的工具。
- **Patti 推荐**：模型调用搜索工具 → 活动搜索把参数转成推荐查询（默认软条件）→ 对话用例经只读接口取推荐排序结果 → 活动搜索生成推荐卡 → 结果交回模型写回复 → 流式返回回复与推荐卡。点卡只用于跳转，不写入。
- **Conor 创建活动**：模型调用预填工具 → 对话用例经只读接口取节日与标签等固定列表 → 活动草稿校验字段、标明来源、生成草稿卡 → 流式返回。App 把草稿交给 Create 视图模型预填表单，用户点 Create 才发布（B3，iOS App C3 边 9）。
- **Lily 整理资料**：模型调用摘要工具 → 资料摘要校验条目、生成摘要卡 → 流式返回。用户逐条勾选确认后，由 App 经业务接口写入（B6）。
- **校验失败**：工具组件拒绝参数时不生成卡片，把原因交回模型改正一次，计入每轮的保护上限；仍不通过，角色回复没能生成可用的结果、请换个说法（V8，Demo 架构方案第 10.6 节）。
- **暂不可用**：模型服务出错，或保护措施触发（工具调用次数或等待时间达到上限）时，结束本轮并提示 AI 暂不可用，其他功能照常（S3-1）。

## 5 评审清单回执（规范第 9 节）

违反项列为问题，编号接续 P1–P5 与 O1–O3。

**依赖方向**

- 跨类别箭头从技术指向业务：对话接口适配器 → 对话用例（边 2）符合。对话用例调用两个适配器（边 8、9）的运行时方向是业务到技术，但模型口由对话用例定义、只读接口由 API 服务的业务侧定义，源码依赖反向，符合。外部技术只出现在适配器到外部节点的边 10、11 上。
- 每个接口定义在中心侧：边 1、2 的接口归 AI 编排服务的业务侧；边 3–7 归各规则组件；边 8 的模型口归对话用例；边 9 的只读接口归 API 服务的业务侧，与 iOS App C3 边 7 的做法相同。边 10、11 的接口归外部，这正是适配器存在的原因。符合。
- 无循环依赖：调用只有“接入 → 对话用例 → 规则与适配器”一个方向，规则组件之间互不调用。符合。

**职责**

- 每个组件一句不含“和”的职责：第 2 节各组件写成“负责 X，不负责 Y”，符合。节点上的概括为了可读，列了两件事。
- 名称过规范第 6 节七条：业务组件用持有之物的名词（角色目录、共享上下文、活动草稿、资料摘要），“对话用例”“活动搜索”是名词短语，与 API 服务 C3 的“业务用例”“推荐排序”同类；技术组件用“对象＋角色名词”（接口适配器、适配器、客户端）；中英直译成对；没有 manager、service、engine 一类只表地位的词。符合。
- 应用服务层不含业务判断：对话用例只编排、不判断，同意、上下文范围、参数校验、卡片内容都在规则组件里。这是本图最需要守住的一条，列为观察 O4。

**接口**

- 每根线都有边表行并标了具体接口名：11 条边都有边表行。符合。
- 没有组件向所有调用方暴露同一个大接口：三个工具组件各自只暴露本工具的规则；只读接口客户端只有对话用例一个调用方。符合。
- 接第三家同类供应商要改几个框：换大模型供应商只新增一个实现模型口的适配器，“0 改 1 加”；Demo 的 ScriptedLLMClient 就是一例。符合。
- 测试环境把框换成假实现，上游要不要改：模型口可以换成演示脚本，只读接口可以换成本机的 LocalFestivaAPI，对话用例都不改；五个规则组件是纯规则，不需要假实现就能测试。Demo 本身就是证明。符合。

**耦合与切分**

- 没有两个容器共用数据库表：本服务不访问数据库，也不保存对话。符合。
- 没有按技术分层切服务：三层分组框是容器内部的六边形布局，不是切服务。符合。
- 顶层按业务能力划分，每片内部再分层：三个角色的能力分成活动搜索、活动草稿、资料摘要三个组件，角色与上下文的规则各自成组件。符合。
- 没有只转发不做决策的胶水组件：对话接口适配器在决定“令牌交给 API 服务校验”之后不再鉴权，但它负责 HTTP 请求与用例调用之间、回复流与流式响应之间的协议转换，换协议时只换它，是技术侧的驱动适配器，不是在两个组件之间转发的胶水。只读接口客户端负责协议与令牌携带。符合。

**C2 遗留项的结论**

- C2 假设 1（AI 编排服务怎样验证令牌）：已决定，本服务不自行验证，由 API 服务校验（T0020）。
