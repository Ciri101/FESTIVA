## 1 视图注记

- **本族**：FESTIVA 系统的五个容器（浅蓝，`class app,ai,api,db,files shell`）；蓝色虚线框是系统边界。外部角色与外部系统为灰色，与 [C1](../festiva-c1/festiva-c1.md) 同名。
- **线型**：实线表示发起调用或写入，虚线表示只读或投递（规范第 5 节）。AI 编排服务到 API 服务画成虚线，因为 AI 只查询、不写入（B1）；所有写入都经 iOS App 到 API 服务的边 2，在用户确认后发出。
- **数据边界**：只有 API 服务读写数据库；AI 编排服务与 App 都不直接访问数据库。数据库与文件存储是系统专属的存储，脱离 FESTIVA 没有意义，所以留在系统框内（规范第 3 节）。检查工具不认圆柱写法，两者画成方框。
- **推荐排序**：是 API 服务内的组件，不单独成为容器（任务 T0013 中的决定）。理由与重新评估的条件见工程架构文档第 3 节。
- **技术标签**（任务 T0016 的决定）：API 服务与 AI 编排服务都写“Swift · 容器部署”，两者用 Swift 编写、沿用 Demo 的业务核心与 AI 模块，在同一容器平台上分别部署；数据库写“托管 PostgreSQL”；文件存储写“S3 兼容对象存储”；云端大模型服务写“Qwen API（暂定）”；邮件发送服务写“服务商待定”。R5 的托管后端服务评估后未采用，理由见工程架构文档第 3 节。容器平台、Swift 服务端框架、邮件与对象存储的具体供应商暂缓，都不影响本图的结构。
- **布局**：纵向。系统框在上，外部系统排成一行；“学生 → App → API 服务 → 邮件 → 学生”构成一个环，默认渲染头会把国际学生排在最下面，“使用”这条线从底部绕到 App。

## 2 容器注记

“类”按规范第 4 节的四个问题判断：规则变了是否必须改它、业务方能否判断它的对错、换个行业是否还需要它、市面上能否买到。

| 容器 | 英文名 | 类 | 一句职责 | 技术标签 | 依赖谁 |
| --- | --- | --- | --- | --- | --- |
| iOS App | iOS app | 业务 | 负责把用户操作变成业务请求，不负责业务规则的最终判定，也不持有任何密钥 | Swift / SwiftUI | API 服务、AI 编排服务、文件存储、Apple 地图服务、Apple 推送通知服务 |
| API 服务 | API service | 业务 | 负责业务规则的唯一执行，不负责调用大模型 | Swift · 容器部署 | 数据库、文件存储、邮件发送服务、Apple 推送通知服务 |
| AI 编排服务 | AI orchestration service | 业务 | 负责把用户的对话请求变成本板块工具的结构化结果，不负责写入任何数据 | Swift · 容器部署 | API 服务（只读）、云端大模型服务 |
| 数据库 | database | 技术 | 负责持久化全部业务数据，不负责任何业务判断 | 托管 PostgreSQL | — |
| 文件存储 | file storage | 技术 | 负责保存封面图与头像的图片文件，不负责决定谁能上传（由 API 服务签发地址） | S3 兼容对象存储 | — |

- iOS App 与 AI 编排服务在容器层标为业务，但内部各有技术部分：App 里的 API 客户端与定位，AI 编排服务里的大模型适配器。按规范第 4 节，判不清的部分要拆成两个组件，这在各自的 C3 评估时处理。
- 节点上的职责是容器级的概括，列了不止一件事；“一句不含‘和’的职责”这条要求在 C3 组件层严格执行。

## 4 评审清单回执（规范第 9 节）

违反项列为问题，编号与第 5 节“发现的问题”一致；C1 的 P1 在本层同样成立，沿用同一编号。

**依赖方向**

- 跨类别箭头从技术指向业务：本区箭头画的是运行时调用方向，依赖方向按边表的耦合项判断。业务容器调用技术容器或外部系统的边中：边 8、11、12 的接口由业务侧定义，外部供应商由适配器接入，符合；**边 9 是业务侧对数据库的源码依赖，列为问题 P2**；**边 4、10 的接口归对象存储，列为问题 P3**；**边 5、6 属于问题 P1**。
- 每个接口定义在中心侧：边 2、7 的接口归 API 服务，边 3 的接口归 AI 编排服务，边 8、11、12 的接口由调用它的业务容器定义，都符合；不符合的是边 4、5、6、9、10，分别归入 P1、P2、P3。
- 无循环依赖：容器之间的调用是 App → AI 编排服务 → API 服务、App → API 服务，没有反向调用；边 6 与边 13 在 App 与推送服务之间构成的往返是平台回调与投递，不是源码循环。符合。

**职责**

- 每个组件一句不含“和”的职责：容器注记的职责各为一句，写成“负责 X，不负责 Y”，符合。节点上的概括列了多件事，见第 2 节的说明。
- 组件名过规范第 6 节七条：中英文名直译成对（第 2 条）、英文名取含义固定的词（第 3 条）、存储以存储名出现（第 4 条），符合。**“API 服务”“AI 编排服务”含只表地位的“服务”（第 1、6 条），列为问题 P4**；这是用户在 T0013 中明确作出的决定，记为已知偏离。
- 应用服务层不含业务判断：在 C3 判断。

**接口**

- 每根线都有边表行并标了具体接口名：14 条边都有边表行；检查 (w) 逐边等价。符合。
- 没有组件向所有调用方暴露同一个大接口：AI 编排服务只拿到只读的一部分（边 7），不同于 App 使用的完整业务接口（边 2），符合。API 服务的接口按业务能力再细分，在 C3 处理。
- 接第三家同类供应商要改几个框：大模型、邮件都是“0 改 1 加”，适配器分别在 AI 编排服务与 API 服务内；对象存储换供应商只改 API 服务里签发地址的适配器，App 只按签名地址上传，不受影响。符合。**地图不符合，见 P1。**
- 测试环境把框换成假实现，上游要不要改：大模型（Demo 的演示脚本即是一例）、邮件、推送、数据库、文件存储都可以替换，上游不改，符合；**地图显示除外，见 P1**。

**耦合与切分**

- 没有两个容器共用数据库表：只有 API 服务读写数据库。符合。
- 没有按技术分层切服务：AI 编排服务单独成为容器，理由是密钥隔离（D1）与写权限隔离（B1），属于安全边界，不是“前端服务／逻辑服务／数据服务”式的技术分层。符合。
- 顶层按业务能力划分，每片内部再分层：API 服务一个容器承担了认证、活动、申请与名额、推荐排序、通知等全部业务能力，按业务能力的划分落在它的组件层。以现在的产品规模可以接受，列为观察 O1。
- 没有只转发不做决策的胶水组件：AI 编排服务负责选择角色、装配上下文、校验输出，不只是转发。符合。

## 5 回述（规范第 10 节）

1. **组件职责表**：见第 2 节容器注记（含“类”栏）。
2. **接口清单**：工程架构文档第 3 节的 C2 边表，共 14 条，写明签名、归属、同步或异步与耦合。
3. **做出的假设**（请用户确认）：
   - 假设 1：用户令牌由 API 服务签发；AI 编排服务收到对话请求后，用同一令牌代用户查询（边 3、7）。它怎么验证令牌（本地验签，还是询问 API 服务）未定。
   - 假设 2：App 按图片地址直接从文件存储读取图片；图片地址是公开地址还是带签名的地址未定。
   - 假设 3：AI 同意状态由 API 服务记录，AI 编排服务每次对话经边 7 查询（工程架构文档第 5.3 节）。
   - 假设 4：设备令牌经边 2 登记到 API 服务。
   - 假设 5：本图按对话记录不在服务端保存来画；如果决定保存，保存在哪个容器还要再定（工程架构文档第 5.3、15 节）。
4. **规格里没有定义的边界**（需要用户决定）：
   - 边界 1：流式对话的超时与断线重连；每轮对话调用工具的次数上限（Demo 定为 2 次，正式产品未定）。
   - 边界 2：AI 编排服务调用 API 服务的限流，以及 API 服务不可用时怎么降级。
   - 边界 3：图片的大小与格式限制、签名地址的有效期、上传后没有发布活动时的图片清理、图片内容审核。
   - 边界 4：API 服务多实例运行时，名额事务的隔离级别与加锁方式。
   - 边界 5：通知记录与推送的幂等，以及推送失败后是否重试。
   - 边界 6：用户注销账号时，业务数据与图片怎么处理。
5. **发现的问题**：
   - **P1**（同 C1）：边 5（地图）与边 6（注册设备）使用 Apple 平台接口，接口不在中心侧。修法与建议见 [C1 设计说明](../festiva-c1/festiva-c1.md)第 4 节。需要用户决定。
   - **P2**：边 9，API 服务对数据库是源码依赖，接口归数据库，属于业务侧依赖技术侧。后果：表结构或数据库一变，业务规则的代码跟着改；业务规则难以脱离数据库测试。修法：在 API 服务的 C3 中由业务侧定义存取接口（仓储口），数据库适配器实现，依赖方向因此倒转。容器层的边保持不变，建议在评估 API 服务的 C3 时落实。需要用户决定。
   - **P3**：边 4、10，文件存储的上传与读取接口归对象存储，App 直接按签名地址上传。评估：谁能上传什么仍由 API 服务签发地址来决定，App 只做通用的上传；换对象存储供应商只影响 API 服务里的适配器。建议接受，并在 API 服务的 C3 中由它定义图片上传接口。需要用户决定。
   - **P4**：容器名“API 服务”“AI 编排服务”含只表地位的“服务”，不符合规范第 6 节第 1、6 条。用户已在 T0013 中决定保留，理由是与产品设计文档、Demo 架构方案的用语一致，改名会超出本任务范围。记为已知偏离，不再请用户决定。
   - **观察 O1**：API 服务承担全部业务能力，按业务能力的划分要在它的组件层体现。它是 C3 评估的首要候选。
