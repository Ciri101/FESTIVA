# truth 文档修订与定稿

## 来源与目的

2026-09-29，用户（老师）在当前对话中指令“采纳全部裁决，登记任务开始修订”，并“同意拆分和依赖”。随后老师调整文档结构：核心文档为“产品设计”与“工程架构”两份，高保真设计文档属于 UI 设计，移入老师新建的 truth/ui/；老师“确认结构和分工，授权撤回重新批准”。本任务为父任务，下设 5 个子任务：文件结构调整、goals.md 修订、产品设计文档编写、工程架构文档修订、UI 设计文档修订。

裁决由学生在“FESTIVA 定稿裁决单”（私有页面 https://claude.ai/artifact/C4rCZ1czzVZKn9dYUPNyZy ，读取于 2026-09-29）上逐题作出，共 38 题：第一轮 32 题（A–F 组）、追问 R1–R6。裁决单中的“评审建议”为 Agent 起草的意见，不是授权；授权来自老师采纳。老师在对话中说明本项目用途：拍摄 Demo 视频、在 GitHub 开源、用于研究生产品设计申请。

目的：依据这些裁决，把 truth/ 下两份草稿与 goals.md 修订为可逐节确认、可定稿的基线。本节是全部裁决的唯一记录处，truth 文档只链接到本任务，不复制整段裁决。

- **R2 Me 页的 Address 要不要删？** → A：删掉 Address（同评审建议）
- **R3 性别字段的规则怎么定？** → C：只有 女 / 男 两个选项，注册时必填（评审建议 A）

- **R5 服务端采用哪种方案？** → A：托管后端服务（BaaS，例如 Supabase），按左侧的最简形态（同评审建议）

  - 学生备注：注意：系统机构图我们还是按照正式产品级标准去画，目前的简化方案只是针对我们的 Demo 开发版本，你可以明白吗？

### A 范围与定位

- **A1 Demo 要真正跑通到什么程度？** → B：最小闭环：SwiftUI + 简单 API + 数据库，跑通“浏览 → 详情 → 申请 → 主办审批”和“创建活动”；AI 只真实接入一个角色（同评审建议）
  - 学生备注：最好还可以支持录制逼真的演示视频。
- **A2 首发城市是否锁定温哥华？** → A：Demo 只做温哥华：币种 CAD、时区 America/Vancouver、学校名单固定（同评审建议）
  - 学生备注：但是地图本身不限制，只是说我们演示区域限制于“温哥华”。
- **A3 源设计文件里还有没导出的画板吗？** → B：没有更多，以现有 10 张为准，缺的页面由文档定义（评审建议 A）
- **A4 C4 里写了、高保真没画的能力，怎么处理？** → A：按建议分别处理：学生验证补一个简单流程；详情页显示预计通勤时间；安全功能 Demo 只保留活动规则；日程、文化提示、推荐反馈在 C4 里标为“后续版本”（同评审建议）
  - 学生备注：因为这个 C4 图早于 UI 设计，所以当时功能定位收敛得不够清晰，可能包含了很多不必要的功能设定。

### B AI 角色

- **B1 AI 的产品形态：三个对话角色，还是嵌入式推荐？** → C：保留角色和对话入口，但对话只用来收集条件；AI 的产出都变成卡片或预填表单，用户确认后才生效（同评审建议）
  - 学生备注：补充：当初设计就是每一个角色负责一个功能板块，你建议的机构化流程对话是针对其各自负责的功能，但是这应该是 Agent 基于用户的请求而智能触发的，每个角色 Agent 依然可以和用户对话，就像是 AI 客服一样，可以聊天回复问题，也会给出结构化的输出。
- **B2 三个角色之间共享什么信息？** → A：只共享用户确认写入资料的字段，不共享对话原文（同评审建议）
  - 学生备注：共享的其实就是用户画像和用户的创建或参与的派对信息。本质属于用户自身的数据。
- **B3 Conor 生成的活动，怎样才算生效？** → A：点卡片打开预填好的 Create 表单；AI 补的字段标成“建议”，用户点 Create 才发布（同评审建议）
  - 学生备注：AI 给的是预填稿，最终定稿需要用户完成确认。
- **B4 Patti 怎么对待用户的“偏好”？** → A：用户偏好默认只影响排序；用户明确说“必须/只要”时才变成硬条件，并在对话里说明“已按 X 过滤”（同评审建议）
- **B5 匹配度和推荐理由怎么展示？** → B：去掉百分比；卡片上显示 2–3 个理由标签（如“中文交流”“人均 ≤ $35”“8 km 内”），详情页列出不符合的地方（同评审建议）
- **B6 Lily 怎样写入个人资料？“private chat”要不要改？** → A：Lily 生成一段资料摘要，用户逐条勾选确认后才写入；开场去掉 “private”，或说明对话会由 AI 服务处理（同评审建议）
  - 学生备注：AI 可以基于用户请求信息帮助整理和代写，但是需要给用户亲自确认的交互卡片。
- **B7 要不要做“人与人匹配”？** → A：不做，只推荐活动；Lily 这句改成“优先推荐氛围轻松的小型聚会”（同评审建议）

### C 数据与规则

- **C1 “Verified” 到底验证的是什么？** → A：只有一种：在校学生身份（学校邮箱验证），统一显示为“学校 · Verified student”（同评审建议）
- **C2 活动有哪些字段？Create 表单要补哪些？** → A：补齐 Create：加节日、语言、结束时间、标签、结构化的限制条件；交通方式不作为活动字段（同评审建议）
  - 学生备注：可以直接评估和移除与“派对”本身无关的信息项。
- **C3 “Girls only” 这类限制怎么执行？** → B：用户资料增加性别字段，系统自动拦截不符合条件的申请（评审建议 A）
  - 学生备注：性别属于用户公开信息之一。
- **C4 申请、审批和名额按什么规则走？** → A：按右侧建议的规则：通过才占名额；满员时关闭申请；申请人可撤回；主办人拒绝不必填理由；Me 页加“我的申请”查看结果；主办人取消活动时通知所有人（同评审建议）
- **C5 活动地址什么时候公开？** → A：获批前只显示大致区域（街区名和距离），获批后显示精确地址（同评审建议）
- **C6 时间怎么记录和显示？** → A：按活动所在地（温哥华）时间存储和显示，带年份；星期由系统根据日期生成；增加结束时间（同评审建议）
- **C7 预算是什么意思？** → A：人均预计花费，单位 CAD，取整；筛选按“最高可接受的人均”过滤（同评审建议）
- **C8 筛选页：距离从哪里算？交通方式起什么作用？** → B：只用当前定位；交通方式只作为标签筛选（评审建议 A）
  - 学生备注：追问：“交通方式”属于有效的筛选标准吗？感觉和距离没关系啊！还是说是一种交通可达性的筛选？
- **C9 个人资料里的敏感信息谁能看、用在哪？** → A：默认只有本人可见，只用于推荐；饮食过敏可以在申请时选择分享给主办人；发给外部 AI 前先征得同意（同评审建议）
